# 0.2.1 — Resource Module (RM)

## 2.1. Назначение

Resource Module (RM) — механизм организации и в[= rule.txt](..%2Fdd%2F%3D%20rule.txt)ызова ресурсов приложения.

Он объединяет связанные компоненты, шаблоны и другие ресурсы в отдельные наборы ресурсов. Такой набор может соответствовать сайту, приложению, подсистеме или отдельной предметной области.

Примеры наборов ресурсов:

- `rb` — базовые ресурсы;
- `site` — ресурсы сайта;
- `app` — ресурсы приложения;
- `komar` — условный набор ресурсов конкретной предметной области.

Название прикладного набора ресурсов выбирается по смыслу проекта.

## 2.2. Общая структура

Набор ресурсов представляет собой отдельную директорию. Внутри него располагаются компоненты и ресурсы, относящиеся к этому набору.

Пример:

```text
resources/
├── rb/
├── site/
│   ├── header/
│   ├── footer/
│   └── ...
└── komar/
    ├── header/
    ├── footer/
    └── ...
```

Имена директорий пишутся **в нижнем регистре**.

Это относится как к самим наборам ресурсов, так и к вложенным папкам компонентов: `site`, `komar`, `header`, `footer` и т. д.

Не использовать варианты вида `Site`, `Komar`, `Header`, `Footer`.

## 2.3. Набор ресурсов

Набор ресурсов — самостоятельная область, через которую внешний код получает доступ к находящимся внутри ресурсам.

Например, для набора `site` внешний код работает через интерфейс `site`, а для `komar` — через `komar`.

Набор не должен требовать от вызывающего кода знания своей внутренней файловой структуры.

Внешний код говорит, **что ему требуется**, а RM определяет, где это находится и как это подключить.

## 2.4. Компоненты

Внутри набора ресурсов находятся компоненты.

Например:

```text
site/
├── header/
├── footer/
└── menu/
```

Компонент может содержать собственный PHP-класс, шаблон, CSS, JavaScript, изображения и другие необходимые ему файлы.

Компонент по возможности хранит относящиеся к нему ресурсы рядом с собой.

Это позволяет переносить и изменять компонент как относительно самостоятельную единицу.

## 2.5. Внешний API набора ресурсов

Для каждого набора ресурсов существует короткий внешний интерфейс.

Например, набор `site` предоставляет вызовы семейства `site(...)`.

Через этот интерфейс можно получить нужный ресурс или информацию о нём, не обращаясь напрямую к физическому пути файла.

Принцип:

```text
внешний код
    ↓
site(...)
    ↓
Resource Module
    ↓
нужный компонент / ресурс
```

## 2.6. Человекоподобный вызов

Основной вызов должен быть коротким и удобным для повседневного использования.

Он предназначен для наиболее частых операций и по смыслу напоминает человекопонятный интерфейс.

Пример общей идеи:

```php
site(...);
```

Вызов скрывает технические детали поиска и подключения ресурса.

## 2.7. Низкоуровневый вызов

Помимо короткого интерфейса может существовать более низкоуровневый программный вызов.

Он нужен там, где требуется передавать дополнительные параметры, объекты или точнее управлять поведением RM.

Условно:

```text
site(...)       — короткий повседневный вызов
__site(...)     — более низкоуровневый программный вызов
```

Точное API должно соответствовать фактической реализации фреймворка. Не следует придумывать новый интерфейс, если необходимый механизм уже существует.

## 2.8. Шаблоны

Одна из основных задач RM — удобный вызов шаблонов компонентов.

Для этого используется короткий helper набора ресурсов.

Например:

```php
echo site_tpl('footer');
```

Смысл вызова: получить и вывести шаблон компонента `footer` из набора ресурсов `site`.

Вызывающий код не должен вручную собирать путь до файла шаблона.

Аналогичный принцип применяется и к другим наборам ресурсов.

## 2.9. Контекст и изоляция

Каждый набор ресурсов образует собственный контекст.

Например, `footer` внутри `site` относится именно к набору `site`. Другой набор ресурсов может иметь собственный `footer` с другой реализацией.

```text
site/footer
komar/footer
```

Одинаковые названия компонентов в разных наборах ресурсов не означают, что это один и тот же компонент.

Это позволяет держать связанные ресурсы локально и уменьшать связанность между частями приложения.

## 2.10. Основная модель

Базовая модель RM:

```text
Resource Module
    ↓
Resource Set
    ↓
Component
    ↓
Resources
```

На практическом уровне:

```text
RM
└── набор ресурсов (`site`, `app`, `komar`, ...)
    └── компонент (`footer`, `header`, ...)
        └── ресурсы компонента
            ├── PHP
            ├── template
            ├── CSS
            ├── JS
            ├── images
            └── другие файлы
```

То есть RM является общим механизмом, набор ресурсов группирует предметно связанные компоненты, а компонент объединяет относящиеся к нему файлы и поведение.

### RB — обязательный базовый набор ресурсов

`rb` (`RB`, Base Resources) — базовый набор ресурсов фреймворка.

В нём находятся базовые компоненты и ресурсы, на которые могут опираться прикладные наборы ресурсов.

При переносе или копировании ресурсной части фреймворка `rb` необходимо переносить обязательно вместе с ней.

Прикладные наборы (`site`, `app`, `komar` и другие) могут меняться от проекта к проекту, но `rb` рассматривается как базовая часть RM.

При этом имя директории на диске следует правилу нижнего регистра:

```text
rb/
```

Обозначение класса или сущности в коде может оставаться `RB`, если именно так оно называется в существующей реализации.

---

## Ключевые правила 0.2.1

1. RM организует доступ к ресурсам через наборы ресурсов и компоненты.
2. Внешний код не должен зависеть от физических путей к ресурсам.
3. Компонент хранит связанные с ним файлы максимально локально.
4. Все директории RM именуются в нижнем регистре.
5. `rb` — базовый набор ресурсов и обязательная часть при переносе RM.
6. Прикладные наборы ресурсов могут называться по смыслу проекта: `site`, `app`, `komar` и т. п.
7. Существующий API фреймворка имеет приоритет: документ описывает его, а не вводит новую архитектуру без необходимости.
