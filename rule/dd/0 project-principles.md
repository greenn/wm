# 0.1 — Project Principles

## Статус документа

Промежуточная фиксация базовых принципов проекта и правил работы AI-агентов с фреймворком.

Этот документ не описывает всю архитектуру фреймворка. Он фиксирует исходную философию и ограничения, которые должны сохраняться при дальнейшей подготовке `AGENTS.md` и вспомогательной документации.

---

## 1. Главная философия фреймворка

Основной принцип фреймворка — **простота**.

Фреймворк должен позволять создавать сайты, страницы и небольшие приложения с минимальным количеством обязательной инфраструктуры.

Предпочтение всегда отдаётся:

- простому решению вместо сложного;
- слабой связанности вместо глубокой зависимости компонентов;
- явному и понятному коду вместо архитектурных абстракций ради самих абстракций;
- возможности использовать отдельные части системы независимо;
- минимальному количеству обязательных действий для запуска новой страницы или функции.

Не следует искусственно добавлять:

- сложные цепочки наследования;
- лишние уровни абстракции;
- обязательные контейнеры зависимостей;
- сложные роутеры там, где достаточно файла;
- обязательную сборку фронтенда;
- архитектурные шаблоны только потому, что они считаются «современными».

Фреймворк сознательно может быть проще традиционных PHP-фреймворков.

---

## 2. Простое создание страниц

Одна из базовых возможностей проекта — страница может существовать как самостоятельный файл.

Пример:

```text
page3.php
```

или:

```text
about/
└── info.html
```

Для простой страницы не должно требоваться создание дополнительных контроллеров, моделей, маршрутов или регистрационных файлов, если текущая архитектура этого не требует.

Если задачу можно решить одним файлом — это допустимый и предпочтительный вариант.

Усложнение допускается только тогда, когда оно действительно необходимо задаче.

---

## 3. Минимальная связанность

Компоненты проекта должны по возможности оставаться независимыми.

Ресурсы могут находиться в разных местах проекта и подключаться через существующие механизмы фреймворка.

Данные сайта также не должны быть жёстко привязаны к одному формату хранения.

Допустимые источники данных могут включать:

- JSON;
- текстовые файлы;
- PHP;
- базу данных;
- другие существующие в проекте источники.

Не следует без необходимости заменять эту универсальность единой обязательной системой хранения.

---

## 4. Темплейтер и ресурсы

Основная работа сайта строится вокруг существующего **темплейтера ресурсов**.

Ресурсы могут располагаться в разных частях проекта и подключаться в нужное место через существующий класс/механизм-коннектор.

Точная структура, API и правила работы темплейтера и коннектора будут дополнительно зафиксированы после анализа исходного кода проекта.

AI-агент не должен придумывать новый механизм ресурсов, если существующий решает задачу.

---

## 5. Используемые технологии

Основной стек проекта:

- PHP;
- HTML;
- CSS;
- JavaScript.

Во фронтенде могут использоваться:

- jQuery;
- Lodash;
- Vue 3 через CDN для более сложных интерфейсов.

Проект не требует обязательного frontend build pipeline.

Не следует автоматически добавлять:

- npm;
- Vite;
- Webpack;
- TypeScript;
- SPA-архитектуру;
- новые CSS/JS-фреймворки;

если этого прямо не требует задача.

Внешние библиотеки могут подключаться при необходимости, но не должны становиться обязательной зависимостью всего фреймворка без явного решения владельца проекта.

---

## 6. PHP-функции

Основное расположение PHP-функций:

```text
web/php/
```

Если требуется новая общая функция, она создаётся отдельным файлом.

Пример:

```text
web/php/new_x.php
```

Подключение выполняется существующим механизмом фреймворка, предварительно обозначенным как `needphp` или аналогичным ему.

Пример концепции:

```php
needphp('new_x');
```

Если функция находится во вложенной папке:

```text
web/php/sub/new_x.php
```

она должна подключаться через соответствующий путь:

```php
needphp('sub/new_x');
```

Точное имя и сигнатура функции подключения должны быть подтверждены по исходному коду.

---

## 7. Локальные функции конкретного модуля

Если новой функции `new_x` требуются дополнительные функции, которые относятся только к ней и не являются универсальными, они должны размещаться рядом с ней в отдельной подпапке.

Пример:

```text
web/php/
├── new_x.php
└── new_x/
    ├── dop1.php
    └── dop_n.php
```

Не следует автоматически переносить локальные вспомогательные функции в глобальную область проекта.

Общая функция становится общей только тогда, когда для этого действительно есть причина.

---

## 8. Blank-файлы и заготовки

Повторно используемые заготовки, шаблоны структур и файлы для ручного копирования могут храниться в папках `blank`.

`blank` — это не мусор и не временные файлы.

Это намеренно сохранённые заготовки, которые владелец проекта может вручную:

1. скопировать;
2. изменить;
3. использовать как основу новой реализации.

AI-агент не должен удалять или «оптимизировать» такие файлы только потому, что они непосредственно не участвуют в выполнении программы.

---

## 9. Консервативный режим работы AI-агента

По умолчанию агент работает **максимально консервативно**.

Главное правило:

> Не менять существующий код без необходимости для выполнения конкретной задачи.

AI-агент не должен самостоятельно проводить рефакторинг только потому, что считает другой вариант архитектурно лучше.

Рефакторинг существующего кода допускается только:

- по прямому запросу;
- либо когда без изменения существующего кода невозможно выполнить поставленную задачу.

Даже во втором случае изменения должны быть минимальными.

---

## 10. Принцип минимального diff

При выполнении задачи следует изменять минимально необходимый объём кода.

Не нужно одновременно:

- менять форматирование соседних участков;
- переименовывать переменные без необходимости;
- переставлять функции;
- переписывать рабочие конструкции в другом стиле;
- обновлять синтаксис только ради современности;
- проводить побочную чистку файла.

Если задача требует изменения трёх строк, предпочтительно изменить три строки, а не переписывать весь файл.

---

## 11. Сохранение существующих комментариев

Комментарии являются частью проекта и должны сохраняться.

AI-агент не должен без прямого указания удалять:

- обычные поясняющие комментарии;
- заметки владельца проекта;
- временные комментарии;
- исторические комментарии;
- закомментированные предыдущие реализации;
- старые куски кода, намеренно сохранённые в комментариях.

Закомментированный код может использоваться как локальная история развития конкретного участка проекта.

Не следует считать его автоматически «мёртвым кодом», который необходимо удалить.

---

## 12. Сохранение стиля проекта

При добавлении нового кода необходимо сначала изучить соседние существующие файлы.

Новый код должен соответствовать текущему стилю проекта, даже если агент предпочёл бы другой стиль.

Приоритет:

1. существующие соглашения проекта;
2. простота;
3. минимальный diff;
4. общепринятые внешние рекомендации.

Не наоборот.

---

## 13. Обратная совместимость

Существующее поведение проекта следует считать значимым.

По умолчанию агент не должен:

- ломать старые вызовы;
- менять публичные интерфейсы;
- удалять старые параметры;
- переименовывать существующие функции;
- менять структуру путей;
- переносить файлы;

если это прямо не требуется задачей.

При наличии нескольких решений предпочтительно то, которое сохраняет текущую совместимость.

---

## 14. Предложения улучшений

AI-агент может обнаруживать потенциально более удачные решения.

Такие идеи разрешается предлагать, но их нельзя автоматически внедрять.

Предлагаемое улучшение должно быть явно отделено от выполняемой задачи.

Формат поведения:

- сначала выполнить задачу в рамках текущей архитектуры;
- затем, при необходимости, кратко указать альтернативный вариант;
- не применять альтернативу без явного запроса.

---

## 15. Что агенту запрещено делать по умолчанию

Без явного указания не следует:

- рефакторить рабочий код;
- переписывать старые модули;
- удалять комментарии;
- удалять закомментированный код;
- удалять `blank`-заготовки;
- менять архитектуру;
- вводить новые обязательные зависимости;
- создавать сложную структуру там, где достаточно простого файла;
- переводить проект на другой framework;
- внедрять build pipeline;
- менять стиль проекта на свой;
- проводить массовое форматирование;
- объединять небольшие независимые функции в большие классы только ради «чистой архитектуры».

---

## 16. Базовый принцип выбора решения

Если существует несколько способов выполнить задачу, предпочтительный порядок такой:

1. Решение в существующем стиле проекта.
2. Решение с минимальным количеством изменений.
3. Решение с минимальным количеством зависимостей.
4. Решение, которое проще понять и вручную изменить.
5. Более сложная архитектура — только если предыдущих вариантов недостаточно.
