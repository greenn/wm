WM — Git workflow

Базовое правило

Если repository подключён к Git и владелец не указал иное, завершённые изменения
оформляются автоматически: атомарный commit, повышение PATCH и push напрямую в
`main`. Pull request не создаётся.

Атомарность

- Разбивать большой запрос на разумные самостоятельно проверяемые подзадачи.
- Одна завершённая подзадача = один commit = одно повышение PATCH.
- Не дробить единое изменение искусственно только ради нескольких commits.
- Не объединять независимые результаты в один commit, если их можно безопасно
  проверить и описать отдельно.

Перед commit

1. Проверить status и отличить свои изменения от пользовательских.
2. Не отменять staged, unstaged или untracked изменения владельца.
3. Добавить в commit только файлы текущей атомарной подзадачи и необходимое
   обновление версии/документации.
4. Выполнить относящиеся к подзадаче проверки.
5. Убедиться, что в diff нет secrets, excluded projects, больших data files и
   случайного форматирования.

Commit

- Сообщение должно кратко описывать результат, а не процесс.
- Версия commit должна соответствовать `0 версионность.md`.
- Не использовать amend, history rewrite, force push или destructive reset без
  прямого указания владельца.

Push

- После успешного commit отправить его в `main` без PR.
- Если remote, authentication, protection rule или конфликт не позволяют push,
  не обходить защиту: сохранить локальный commit и сообщить точную причину.
- Явное указание другой ветки, запрет commit/push или иной workflow в текущем
  запросе имеет приоритет.

Отчёт

Сообщить hash/краткое имя commit, новую версию, выполненные проверки и результат
push. Не объявлять push успешным до подтверждения команды.
