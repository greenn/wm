# Зафиксированные решения владельца

## Статус

Этот документ фиксирует ответы владельца, обязательные для последующих этапов.
Внутри project materials они имеют приоритет над более ранними формулировками
`rule/dd`. Новый прямой ответ владельца может изменить этот список.

## Rule и документация

1. `rule/dd` — концептуальный материал; `rule/ai` должен быть полным,
   непротиворечивым и исполняемым будущим Codex.
2. Полезные дубли разрешены. Документ должен быть понятен самостоятельно.
3. Отсутствующие тематические файлы нужно создавать.
4. `rule/dd/-` и `rule/ai-` исключены из чтения, поиска и изменений.
5. `man/wm` — human Developer Docs; `aidocs` — внутренняя agent-first карта.
6. `man/log` можно вести уже сейчас.
7. `man/sug` содержит пронумерованные предложения; реализация требует approval.

## Версии и Git

1. Базовая версия WM — `20.0.1`; следующий атомарный commit — `20.0.2`.
2. PATCH повышается для каждого commit/атомарной подзадачи.
3. Версия общего `web` отдельна и остаётся `19.2.11`.
4. При подключённом Git commits выполняются автоматически и после проверки
   отправляются непосредственно в `main` без PR, если текущий запрос не задаёт
   иной workflow.
5. Наличие чужих staged/untracked files не разрешает включать их в свой commit
   или отменять.

## Current runtime

1. Каноническая архитектура для нового кода — v2.
2. Целевая версия PHP — 7.2.
3. `short_open_tag=On` обязателен; в project PHP используется только короткая
   форма тегов.
4. Для нового интерфейса используется Vue 3. Vue 2 считается legacy и не
   копируется в новые реализации.
5. jQuery и Lodash остаются допустимыми существующими инструментами.
6. `console.log` включён по умолчанию; отключение вводится отдельным требованием.
7. `title` и tooltips используются по возможности чаще, особенно для неочевидных
   действий.
8. Логотип кликабелен и ведёт на титульную страницу.

## Naming и разработка

1. Новые каталоги, файлы, CSS names и изображения используют kebab-case там,
   где это возможно.
2. PHP/JavaScript variables используют camelCase.
3. Крупные сущности могут использовать PascalCase.
4. Legacy names не переименовываются ради нового соглашения.
5. DRY применяется прагматично: без самовольного рефакторинга и без сложной
   абстракции только ради удаления небольшого повтора.
6. Иногда намеренный повтор допустим, чтобы сначала определить правильную общую
   границу.

## Resource architecture

1. `r` — resource layer, а не единый RM.
2. RM может находиться в любом зарегистрированном месте.
3. `rb` и `lay` — именованные RM. `lay` не обязателен архитектурно, но входит в
   стандартный копируемый набор.
4. `site`, `admin`, `kot` и другие прикладные области также могут быть
   именованными RM.
5. Компонент не существует без обязательного `<component>.class.inc`.
   Директория без него является blank, support directory или частью компонента.
6. IQ подключает окружение сайта/проекта.
7. Library connector имеет путь `web/lib/<name>/<name>.php` и подключается через
   `_lib('<name>')`.
8. RM connector/entry — `<component>.class.inc`; эти три понятия нельзя смешивать.
9. Корневой `api` маршрутизирует запросы к RM.

## Проекты и exclusions

1. `.vmk4` — основной current-пример v2 с `iqSite` и `iqPro`.
2. Dot-project зависит от имени: `.vmk4`, `.ash`, `.gss1`, `.ripr`,
   `.kp`, `.kp2`, `.zo`, `.tosno` и другие.
3. Codex может исследовать dot-project по задаче, но такие проекты не коммитятся
   в WM.
4. `.blank` и `.blank2` сохраняются и коммитятся; они структурно правильны, но
   могут быть технически незавершёнными.
5. Продуктовые и каталожные JSON legacy-проектов нельзя массово читать.
6. Новый проект `wm-0` находится рядом: `J:\dv\wm-0`.
7. Project-owned ядро: `iq.inc`, `index.php`, root `test` и project RM
   (текущий пример — `gss3` с pages/router/components/templates).
8. Стандартно копируются `r/rb` и `r/lay`; `lay` архитектурно опционален,
   но входит в комплект владельца. По потребности добавляются `api`, `css`,
   `fonts`, `i`, `js`, `site`, `wd`.
9. Project settings находятся в `site/settings`, URL-version базы — только в
   `site/uv`.
10. `wm-0` использует общий `web` и общий `man`, не создавая их копии,
    если не выбран отдельный local-web режим.
11. Local web подключается через `site/web/web[self].inc`. Централизованный
    web для локальных/собственных доменов выбирается через
    `site/settings/settings[<domain>].inc` и проверенную connector-цепочку.
12. Project-level инструкция называется стандартно `AGENTS.md`.

## Тесты, API и будущие сущности

1. Тесты по умолчанию находятся в корневом `test`; возле компонента — только
   когда иного практического способа нет.
2. Site RM может работать с данными сам или обращаться к внутреннему admin API —
   выбор делается по смыслу задачи.
3. Файл `2 wb.md` описывает только будущий WebBuilder и не выдумывает его API.
4. Существующая PHP-функция `wb()` — отдельный word bank для морфологии и должна
   документироваться отдельно, без переименования legacy.

## Pages, assets и dev-механизмы

1. Для нового кода каноничны pages v2. PHP-router определяет server page.
2. `vue-router` используется внутри приложения, каталога или корзины для
   client history, но связь с PHP-router сохраняется для initial request,
   прямого URL и reload.
3. Admin entry по умолчанию — физический `/admin/index.php`; другие rewrite
   варианты являются явными project exceptions.
4. Root API ищет `<route>.<method>.inc`, затем `<route>.inc`.
5. `wd` — часто используемый визуальный dev-инструмент с reference/live,
   overlays, opacity и outline.
6. `mqr` используется не всегда; это JS runtime scaler через `[mqr]` и
   transform, а не CSS media queries.
7. `uv` добавляет версию к URL через `qv()` для борьбы с cache; canonical
   directory — `site/uv`.
8. `_i($proSid, ...)` обращается к image environment named project;
   `_i::...` — отдельный static image helper.
