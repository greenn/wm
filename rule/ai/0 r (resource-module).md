# Resource layer и Resource Module

## 1. Два разных понятия

`r` — ресурсный слой и соглашение о размещении ресурсов.

RM, Resource Module, — именованный модуль, через интерфейс которого вызываются
его компоненты, templates и другие ресурсы.

`r` не является одним общим RM. RM не обязан физически находиться внутри
директории `r`: конкретные `site` и `admin` могут находиться в корне проекта или
в другом месте, зарегистрированном framework.

## 2. Именованные RM

Примеры:

- `rb` — базовый именованный RM;
- `lay` — именованный RM layout-ресурсов;
- `site` — именованный RM сайта;
- `admin` или `kot` — именованный RM административной системы;
- другие прикладные RM называются по смыслу проекта.

Одинаковые имена компонентов в разных RM принадлежат разным контекстам.

## 3. Компонент

Настоящий RM-компонент — директория с обязательным entry/connector:

```text
<component-name>/
└── <component-name>.class.inc
```

Компонент не может существовать без `*.class.inc`, соответствующего его имени.
Директория без connector может быть blank, служебной подпапкой, набором assets
или частью другого компонента, но не самостоятельным компонентом.

Рядом с connector компонент может хранить:

- `*.tpl.php` и другие templates;
- action/include-файлы;
- `*.css.php`, `*.js.php` и статические assets;
- Vue template/logic fragments;
- `api/<route>.<method>.inc`;
- изображения, данные, blank и локальные вспомогательные файлы.

Фактический набор не обязан включать всё перечисленное.

## 4. Внешний интерфейс

Внешний код обращается к именованному RM через его зарегистрированный helper или
manager и не должен знать физический путь компонента.

Типовая логика:

```text
caller
  -> named RM interface
  -> RM manager/connector
  -> component connector
  -> template, action, API or asset
```

Конкретное имя helper (`rb(...)`, `site(...)`, `admin(...)` и другие) и его
аргументы всегда проверяются по текущей реализации. Документ не вводит
универсальную сигнатуру поверх существующего API.

## 5. Templates и контекст

Template вызывается через RM helper, когда такой механизм предусмотрен. Не
собирать путь к нему вручную из вызывающей страницы.

Контекст template передаётся существующим способом RM. Компонент должен оставаться
локальной единицей: относящиеся только к нему файлы хранятся рядом, а общие
ресурсы выносятся только при реальной повторной потребности.

## 6. `rb` и `lay` в новом проекте

При создании стандартного проекта копируются:

```text
r/rb
r/lay
```

`rb` рассматривается как базовая часть resource framework. `lay` архитектурно
не обязателен, но входит в стандартную копируемую заготовку, потому что его
ресурсы могут использоваться проектом.

## 7. RM, IQ и libraries не смешиваются

- IQ подключает и описывает окружение сайта или проекта (`iqSite`, `iqPro`).
- Library connector находится в `web/lib/<name>/<name>.php` и подключается через
  `_lib('<name>')`.
- RM connector/entry — обязательный `<component-name>.class.inc` внутри
  компонента.

Один механизм не следует описывать или реализовывать как разновидность другого.

## 8. API routing

Корневой `api` может маршрутизировать запрос к выбранному именованному RM, затем
к компоненту и его endpoint. Типовой endpoint находится внутри компонента:

```text
api/<route>.<lower-http-method>.inc
```

Если текущий router поддерживает fallback `api/<route>.inc`, это должно быть
явно отражено в подробной API-документации. Endpoint не отменяет обязательность
component connector.

## 9. Naming

Новые имена директорий RM и компонентов используют lower kebab-case. Имя
connector совпадает с basename компонента. Legacy-имена, классы и helpers не
переименовываются ради нового правила.

## 10. Правила изменений

- Сначала исследовать current v2 loader и соседний компонент.
- Не создавать параллельный loader или router без прямого требования.
- Не переносить существующий RM ради унификации путей.
- Не превращать служебную папку в компонент без connector.
- Не копировать legacy API в новый компонент, если current v2 уже решает задачу.
- Blank сохранять как blank и явно отмечать его статус.
