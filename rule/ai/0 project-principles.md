# Project principles

## 1. Статус и приоритет

Этот документ задаёт базовый режим разработки WM. Он не заменяет конкретное ТЗ,
`AGENTS.md` или подробные технические документы. Внутри материалов проекта
прямые ответы владельца имеют приоритет над более ранними концептуальными
черновиками.

## 2. Главная философия

Основной принцип WM — простота.

Предпочтительны:

- простое решение вместо сложного;
- слабая связанность вместо глубокой зависимости;
- понятный файл или короткий вызов вместо абстракции ради абстракции;
- возможность использовать отдельные части framework независимо;
- минимальное количество обязательных действий для новой страницы, функции или
  компонента;
- существующий механизм WM вместо параллельной новой архитектуры.

WM сознательно может быть проще традиционного PHP framework.

## 3. Простые страницы допустимы

Страница может быть самостоятельным PHP- или HTML-файлом, если задача не требует
RM, controller, model или отдельного router. Не создавать дополнительные слои
только для соответствия внешнему архитектурному шаблону.

Когда страница уже входит в существующую page/router или RM-модель, использовать
эту модель и не обходить её ручными путями.

## 4. Слабая связанность и источники данных

Ресурсы могут находиться в разных частях проекта и разрешаться существующими
connectors. Источник данных выбирается по задаче и может быть PHP, текстовым
файлом, JSON, базой данных или другим поддержанным источником.

Не вводить единое обязательное storage-решение без прямого решения владельца.
Продуктовые и контентные JSON при исследовании legacy по умолчанию не читать.

## 5. Существующий framework API имеет приоритет

- Не придумывать новый resource loader, если задачу решает RM.
- Не подменять IQ library connector или RM connector: это разные механизмы.
- Не собирать физические пути вручную, если framework уже предоставляет вызов.
- Сначала проверять v2 и current structural example `.vmk4`, учитывая
  зафиксированные в `4 known-issues.md` расхождения.
- Legacy использовать только для совместимости или когда это явно требуется.

## 6. Минимальная инфраструктура

Основной стек: PHP, HTML, CSS и JavaScript. Допустимы уже используемые jQuery,
Lodash и Vue 3 через существующий способ подключения.

Без прямой необходимости не добавлять npm, Vite, Webpack, TypeScript, SPA,
frontend framework, CSS framework, dependency container или обязательную сборку.

## 7. Общие и локальные функции

Если небольшая логика повторяется и вынесение явно упрощает поддержку, использовать
существующую общую функцию или создать подходящий helper. Универсальные
PHP-функции обычно находятся в `web/php`; локальные подфункции конкретной функции
могут находиться рядом в одноимённой подпапке.

Не превращать единичный или пока неустоявшийся код в общую абстракцию заранее.
Существующие сборники вроде `fq` и `str` использовать только после проверки их
фактического API.

## 8. Blank — намеренная заготовка

`blank` — не мусор и не временный файл. Это структура для копирования и
последующей адаптации. Blank может существовать глобально, на уровне проекта или
внутри RM.

Не удалять и не «очищать» blank из-за отсутствия runtime-вызова. `.blank` и
`.blank2` считаются структурно правильными, хотя отдельные части могут быть
технически незавершёнными.

## 9. Консервативный режим

По умолчанию:

- не менять существующий код без необходимости для текущей задачи;
- не выполнять инициативный рефакторинг;
- не переименовывать legacy;
- не менять публичные вызовы, параметры и пути;
- не переносить файлы и не обновлять синтаксис только ради современности;
- не удалять комментарии, заметки владельца или закомментированные реализации;
- не проводить массовое форматирование.

Если изменение существующего кода действительно необходимо, оно должно быть
минимальным и совместимым с текущими вызовами.

## 10. Минимальный diff

Изменять только файлы и строки, необходимые для результата. Сохранять соседнее
форматирование и комментарии. Пользовательские staged, unstaged и untracked
изменения не считать своими и не включать в commit без связи с задачей.

## 11. Стиль проекта

Перед добавлением кода изучить соседние current-файлы. Новый код должен
соответствовать PHP 7.2, short tags, naming и фактическому стилю текущего v2.

Порядок выбора:

1. прямое требование владельца;
2. подтверждённый current-стиль WM;
3. простота и минимальный diff;
4. минимальное число зависимостей;
5. внешняя рекомендация, если она совместима с предыдущими пунктами.

## 12. Обратная совместимость

Старые вызовы и структуры считаются значимыми, пока владелец явно не решил
обратное. Не ломать их ради унификации с новым naming или v2. Новый код не должен
увеличивать legacy-долг: Vue 2 и другие legacy-подходы не копируются в новые
реализации.

## 13. Прагматичный DRY

Повторение можно вынести в функцию или подфункцию, когда это действительно
упрощает решение. DRY не является основанием для широкого рефакторинга.
Допустимо временно или намеренно продублировать небольшой код, если будущая общая
граница ещё неясна или абстракция усложнит задачу.

## 14. Документация и предложения

При изменении поведения обновить соответствующие `aidocs` и human docs в
`man/wm`. Идеи за пределами задачи оформить в `man/sug`, присвоить сквозной номер
и дождаться approval. Предложение не даёт разрешения на реализацию.

## 15. Проверка результата

Перед завершением выполнить минимальный достаточный набор проверок: PHP syntax,
целевой URL/API, тест из `test`, asset loading или визуальная проверка. Не
заявлять о проверке, которая фактически не выполнялась.

## 16. Принцип выбора решения

При нескольких вариантах выбрать:

1. решение в существующем current-стиле;
2. минимальное изменение;
3. наименьшее число зависимостей;
4. вариант, который легче понять и вручную изменить;
5. более сложную архитектуру — только когда предыдущих вариантов недостаточно.
